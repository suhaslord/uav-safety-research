# AegisLand Phase 1 Preregistration — v1

**Status:** frozen before the first full reported experiment  
**Project:** AegisLand — Confidence-Aware Safety Supervision for Vision-Based Autonomous UAV Landing  
**Scope:** simulation only

This document freezes the primary Phase 1 analysis before the first result is promoted as a project finding. It exists to reduce accidental cherry-picking of thresholds, metrics, seeds, or conditions after seeing the data.

## 1. Research question

Can the current uncertainty-aware supervisory layer reduce **unsafe simulated touchdowns** under degraded perception compared with the same landing controller operating without supervisory intervention?

## 2. Primary hypothesis

Across the degraded-perception profiles (`blur`, `low_light`, `occlusion`, and `mixed`), the supervised architecture will have a lower pooled unsafe-touchdown rate than the baseline architecture.

The `clean` profile is treated primarily as a control condition and is not required to show improvement.

## 3. Primary endpoint

**Unsafe touchdown rate**

An episode counts as an unsafe touchdown when the simulated vehicle reaches the ground outside the safety envelope defined in `SimConfig`.

The primary comparison is the pooled degraded-condition unsafe-touchdown rate:

```text
baseline vs supervised
```

using the four degraded profiles only.

## 4. Secondary endpoints

These will be reported but will not replace the primary endpoint after results are observed:

- successful landing rate
- abort rate
- final horizontal error
- final horizontal velocity
- final vertical velocity
- number of supervisor interventions
- mean predicted risk
- maximum predicted risk
- dropout count

## 5. Fixed simulator parameters

Phase 1 uses the current defaults in `src/uav_safety/config.py`:

### Simulation

- timestep: `0.05 s`
- maximum simulated episode time: `45 s`
- initial horizontal position: uniform from `-3.0` to `3.0`
- initial altitude: uniform from `5.0` to `8.0`
- maximum horizontal acceleration: `2.5`
- maximum vertical acceleration: `2.0`
- drag coefficient in the simplified model: `0.12`
- touchdown horizontal tolerance: `0.45`
- touchdown vertical-speed limit: `0.80`
- touchdown horizontal-speed limit: `0.80`
- nominal descent-rate target: `-0.70`
- hold descent rate: `-0.10`

### Supervisor

- hold-risk threshold: `0.68`
- abort-risk threshold: `0.90`
- minimum confidence: `0.12`
- near-ground threshold: `1.2`
- maximum hold budget: `120` simulation steps

These values may be changed in later ablation studies, but the primary v1 result will use the values above.

## 6. Experimental conditions

Five perception profiles are evaluated:

1. `clean`
2. `blur`
3. `low_light`
4. `occlusion`
5. `mixed`

Each profile is run with both:

- baseline architecture
- supervised architecture

This produces 10 experiment cells.

## 7. Trial budget

The preregistered main run uses:

- **500 episodes per profile/controller cell**
- **5,000 total simulated episodes**
- top-level seed: **2026**

The episode-level seeds generated by the runner must be preserved in `episodes.csv` so individual trials can be reproduced.

Exploratory runs with fewer episodes may be used for debugging, but their numbers must not be presented as the preregistered Phase 1 result.

## 8. Analysis plan

For every cell, report:

- number of episodes
- unsafe-touchdown rate
- successful-landing rate
- abort rate
- 95% Wilson confidence interval for binary rates where implemented
- mean final horizontal error
- mean intervention count
- mean maximum predicted risk

### Primary comparison

Pool the four degraded profiles and compare the baseline and supervised unsafe-touchdown rates.

Report:

1. absolute risk difference
2. relative risk when mathematically defined
3. raw event counts and denominators
4. uncertainty interval where supported by the analysis code

No single profile may be selected post hoc as the "main" result because it looks strongest.

## 9. Safety–availability tradeoff

A lower unsafe-touchdown rate is not sufficient by itself. A supervisor that aborts almost every trial is not useful.

Therefore the main result must always be shown alongside:

- success rate
- abort rate
- intervention count

Threshold sweeps are **secondary/exploratory** and must be labeled as such. They cannot replace the fixed-threshold preregistered result.

## 10. Exclusion rules

No completed episode may be removed because its result is surprising or inconvenient.

An episode may be excluded only if:

- the program crashes before producing a valid episode record,
- the output is structurally corrupted,
- or a confirmed software bug invalidates the run.

If a bug invalidates a run, the affected experiment must be rerun from the beginning with the fix documented in Git history.

## 11. Stopping rule

The main experiment ends after all 5,000 preregistered episodes complete successfully.

The run must not be stopped early because the result appears positive, negative, or statistically convincing.

## 12. Interpretation rules

### Supported conclusion

If the supervisor lowers unsafe-touchdown rate while preserving a meaningful fraction of successful landings, the project may conclude that the **specified supervisory policy improved safety within this simulation model under the tested perception stresses**.

### Unsupported conclusions

Phase 1 does **not** establish that:

- a real UAV is safer,
- the synthetic perception profiles accurately model a specific camera,
- the supervisor is suitable for deployment,
- or the risk score is calibrated to real-world failure probability.

## 13. Null or negative result policy

A null or negative result will be kept and reported.

If the supervisor does not improve the primary endpoint, the next step is to analyze failure modes and revise the model in a **new versioned experiment**, not quietly change v1 thresholds and rerun until the hypothesis succeeds.

## 14. Reproducibility artifact

The final Phase 1 results folder should contain at minimum:

```text
episodes.csv
summary.csv
summary.md
run_metadata.json
unsafe_touchdown_rate.png
success_rate.png
```

The Git commit used to generate the run should be recorded in the research log.
